# Accessibility & UX specialist report - run 2 (Oct 1 2026)

Read-only review of commit 104e12d. Status after same-day fixes is in [ACTION-ITEMS.md](ACTION-ITEMS.md). Reproduced verbatim from the specialist's final message.

**[major] apps/web/components/AutoSaveIndicator.tsx:84 - `role="alert"` is placed directly on an interactive `<button>`, stripping its implicit button semantics.**
Scenario: `<button role="alert" onClick={() => void retry()}>Save failed — retry</button>`. Explicit ARIA roles override the host element's native role, so assistive tech exposes this control as a live-region alert, not a button - a screen reader is likely to announce only "Save failed — retry" (as inert text) instead of "Save failed — retry, button", losing the cue that it's actionable. Click/Enter/Space still work because it's a real `<button>` element, but the affordance isn't communicated. Every other `role="alert"` in the codebase (grepped: `login/LoginForm.tsx:304`, `AccountMenu.tsx:124`, `FailureSidebar.tsx:55`, `FindingPanel.tsx:145`, `GuestBanner.tsx:106`, `ProjectChat.tsx:284`, `ProjectsCard.tsx:107,167`, `ProseInput.tsx:124`, `ResimulateButton.tsx:117`, `app/error.tsx:24`, `app/global-error.tsx:22`) is correctly on a non-interactive `<p>`/`<div>`/`<span>`/`<main>` - this is the one outlier, introduced in the live-region pass.
Fix: keep `role="alert"` off the button; wrap it instead, e.g. `<span role="alert"><button onClick={...}>Save failed — retry</button></span>`, or drop the role and rely on the text itself plus a separate `aria-live="polite"` sibling announcing the failure.
Confidence: confirmed by reading code.
*(Status: fixed same day - `role="alert"` moved to a wrapping `<span>`, the `<button>` keeps its native semantics. A source-text regression guard test was added (no jsdom in this repo, so the error state can't be reached via `renderToStaticMarkup` without committing an effect), mutation-checked.)*

**[minor/plausible] apps/web/app/login/LoginForm.tsx:231-245 - The Google sign-in slot gives screen-reader users no signal that something is loading, and no fallback if it never loads.**
Scenario: while `googleHeight === null`, the skeleton is `aria-hidden` (correct) and the real button div is `invisible` (correct: `visibility:hidden` removes it from the tab order and accessibility tree while preserving its box for the `ResizeObserver` to measure - this part of the design is sound). But that means a screen-reader user who reaches this region before Google's script has rendered gets nothing at all: no accessible name, no "loading" announcement - indistinguishable from the feature not existing. If they don't think to tab back later, they can miss the Google option entirely. Separately, `onGoogleScriptLoad` is the only path that ever sets `googleHeight`; if `accounts.google.com/gsi/client` is blocked (ad blockers, privacy extensions, or corporate firewalls commonly block Google's GSI script, and this app sets no CSP that would otherwise need updating), the skeleton pulses indefinitely with no timeout, no error text, and no live-region announcement - sighted users at least see continuous visual motion suggesting "still loading," screen-reader users see/hear nothing.
Fix: add a visually-hidden `aria-live="polite"` status (e.g. `<span className="sr-only" role="status">Loading sign-in options…</span>`) mounted alongside the skeleton from first paint, independent of the invisible button div, so SR users get one announcement regardless of where they are in the tab order; optionally add a short timeout (e.g. 4-5s) that reveals a plain-text fallback ("Google sign-in unavailable — use email below") if `googleHeight` is still null.
Confidence: confirmed by reading code for the mechanism; the real-world frequency of GSI-script blocking and actual screen-reader announcement behavior are plausible, not browser-tested.
*(Status: partially fixed same day - the `sr-only role="status"` loading announcement was added. The timeout/fallback for a script that never loads was NOT added - deferred, matches correctness's parallel finding on the same gap.)*

The width calculation (`googleButtonRef.current.clientWidth`) is also sound even while invisible, since an absolutely-positioned `inset-x-0` box with `visibility:hidden` still has real layout geometry.
