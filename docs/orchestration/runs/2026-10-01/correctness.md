# Correctness & reliability specialist report - run 2 (Oct 1 2026)

**[MEDIUM] apps/web/app/login/LoginForm.tsx:192-201 + 176,184 - The Google-button ResizeObserver never disconnects after revealing the button, so it can reproduce the exact reflow it was built to fix.**
Scenario: a browser with an active Google session gets Google's taller personalized "Continue as X" card; the observer (set up once, deps `[]`) measures it and reveals the box at that height (line 197, `style={{height: googleHeight}}` at the wrapper). Google's own async session check then swaps that card to the shorter generic "Sign in with Google" button a couple of seconds later (per the 104e12d commit message, confirmed live). `auto_select: false` and `text: "signin_with"` (lines 176, 184) are explicitly flagged by the author as an *unverified* mitigation for that swap. If it doesn't actually suppress the swap, the still-attached observer fires again on the resulting size change, `setGoogleHeight` updates, and the wrapper's un-transitioned inline height snaps to the new (smaller) value - a visible shrink after the page has settled, for exactly the "common case of a real user testing their own site" the height-measuring fix (95f1539) was written to protect. Not a hydration bug, a real one: the fix only covers the *initial* reveal, not a later content swap.
Fix: add a CSS transition on the wrapper's height so any post-reveal change animates instead of snaps, and verify against a real signed-in-to-Google browser whether `auto_select`/`text` actually suppress the swap (disconnecting the observer after first reveal would avoid the shrink but would also stop tracking a genuine later size change, so a transition is the safer fix).
Confidence: confirmed that the observer persists indefinitely and no transition exists; whether the swap itself still occurs is unverified, as the commit message itself says.
*(Status: fixed same day - `motion-safe:transition-[height] motion-safe:duration-200` added to the wrapper. The observer is still intentionally never disconnected. Whether the swap itself is suppressed remains unverified - needs a real signed-in-to-Google browser.)*

**[MEDIUM] apps/web/components/ProjectsCard.tsx:41-42,154-204 - `deletingId`/`deleteError` are single values shared by every row, so two concurrent deletes cross-talk.**
Scenario: delete project A (confirm sets `deletingId=A`, row A disables/pulses). Before A's `deleteProjectById` resolves, delete project B too (its own confirm overwrites `deletingId` to B at line 196) - A's row now looks idle while still in flight. When A's delete later resolves, its `.then()` (line 199-202) unconditionally does `setDeletingId(null)`, which clears B's still-in-flight "deleting" indicator too, letting the user click B's trash icon again and fire a second, redundant `deleteProjectById(B)` - which reports "Couldn't delete that project. Try again." (line 201) even though B's first delete already succeeded.
Fix: track in-flight deletes as `Set<string>` and per-project errors as `Map<string,string>` instead of one shared id/message.
Confidence: confirmed by reading code.
*(Status: fixed same day - `deletingIds: Set<string>` and `deleteErrors: Map<string,string>`, each keyed by project id; errors render per-project below the (fixed-height) row list, named by project.)*

**[LOW] apps/web/components/ProjectsCard.tsx:42,166-170,192-205 - A failed-delete error never clears except by a subsequent confirmed delete.**
Scenario: delete fails, `deleteError` is set and rendered (line 166-170). The user cancels a later delete confirmation (`onCancel`, line 204) or does anything else entirely - nothing resets `deleteError`; it is only cleared inside the *next* confirmed delete's `onConfirm` (line 194). The stale rose alert sits on screen, now describing nothing the user is doing.
Fix: clear `deleteError` wherever `pendingDeleteId` is set (both the trash-icon click at line 154 and `onCancel` at line 204).
Confidence: confirmed by reading code.
*(Status: fixed same day, folded into the Set/Map fix above - a project's own error clears the moment its trash icon is clicked again, before the confirm dialog even opens.)*

**[LOW] apps/web/lib/sessionStorage.ts:145,196,215,237 + lib/store/slices/projectSlice.ts:215-227 - `listProjects`'s own documented "never throws" invariant is false, and it undermines the loading/error-state fix the sweep just added.**
`currentUserId()` (line 20) is called *before* the `try` in all four exported functions (`saveProject`:145, `loadProject`:196, `listProjects`:215, `deleteProject`:237). `docs/context/web-app-decisions.md:57` explicitly justifies not wrapping `openProject`/`hydrateFromStorage`/`listProjects`'s call sites in `.catch()` by saying they "never throw" - but if `supabase.auth.getSession()` itself throws (a corrupted/blocked storage read), `currentUserId()` rejects outside any try/catch, so `listProjects()` *does* throw, propagating through the un-guarded `refreshProjectList` (called fire-and-forget as `void refreshProjectList()` in ProjectsCard.tsx:46) as an unhandled rejection. `projectsStatus` is left stuck at `"loading"` rather than ever reaching the new `"error"` state the sweep added specifically for this kind of failure - so "Couldn't load your projects / Try again" never shows for the one case it exists to handle, and the UI shows "Loading..." forever instead.
Fix: move `currentUserId(supabase)` inside each function's `try` block (same shape as the already-fixed zero-row update/delete case), or wrap `refreshProjectList`'s body in try/catch and set `projectsStatus: "error"` on catch.
Confidence: confirmed the call sits outside the try/catch and the chain is unguarded, contradicting the stated invariant; whether `getSession()` can actually throw in production is plausible/environment-dependent.
*(Status: fixed same day - `currentUserId(supabase)` moved inside the `try` in all four functions; new test confirms `refreshProjectList` reaches `projectsStatus: "error"` (not stuck on "loading") when `getSession()` throws, mutation-checked.)*
