# Scale, tiers and the minimal start

> Part of the project context; the index is [`CONTEXT.md`](../../CONTEXT.md). How the tier ladder drives instance counts and baseline protections (set by the AI, never by a code threshold), the one-rung-per-Re-simulate rule, and the rule that a build starts minimal at the lowest tier. Read before touching `tierGuide.ts`, `startMinimal.ts`, `workloadTiers.ts` or the reconcile step.

Each section below is one decision: the heading is the decision, the text is the reason and the evidence. A decision marked ~~struck through~~ or "superseded" is kept on purpose, so the reasoning is not lost.

## Instance counts are set by Re-simulate, never reported as a finding

"Single instance / needs more instances / no replicas" was by far the most common finding, and acting on it (queue the fix, Re-simulate) spent a full billed call to flip one trait. `identifyFailures` is now told instance counts are not findings (and no longer offers `SINGLE_POINT_OF_FAILURE` as a code to reach for — the earlier priming lesson applies to codes too), and `dropInstanceCountFindings` removes any that slip through, deterministically: matched on code and title only (never the explanation, where a finding about something else can mention instances), and only for kinds that HAVE an instance count (service, database, load-balancer) — "single point of failure" said of an external dependency is a different risk and stays. In its place `reworkModel`'s prompt makes instanceCount the rework's own job: at the current tier, raise a service to `multiple` / a database to `has-replicas` itself, with a rationale naming the scale, and leave it small while the scale is small. The extended-components step (which owns the load balancer, and was never shown the workload) now gets a one-line `describeScale` so it can size one too. Prompt-driven, not a hard rule: no threshold in code decides what scale "needs" more instances, so it's the model's judgement — if it proves inconsistent, a deterministic tier threshold is the next step.

## Scale moves one rung per Re-simulate

The tier ladders step ~100x, and on the Zoom project 100 → 1M in one go let a single Re-simulate switch on every protection, so nothing ever broke and the review had nothing left to find. The Controls now disable tiers more than one rung above the last simulated tier (`lib/workloadTiers.ts`; tooltip says to Re-simulate first), and `setWorkloadTier` clamps as a backstop. Lowering is always allowed; no baseline (legacy project) means no restriction. Trade-off: reaching a stated 1M target from 100 now takes two Re-simulates (~$0.04–0.09 each).

## A build starts at the minimum for its tier — including protections

Product principle: the starting point is minimal for the selected tier. Investigation (no live run) of a fresh e-commerce build that came out with gateway rate limiting, an order-service circuit breaker and a payment timeout already on: the build prompts' "launch minimal" list named only counts (instances, replicas, write volume, cache TTL), and defined `default` as "the common case" / "typical", which the model reads as typical-in-production for a gateway or a payment call. The reference models do the same ("Typical default for a public-facing gateway"). Fix: both build prompts now list protections as OFF at the starting tier and define "typical" as typical for a first launch, and `startMinimal.ts` enforces it in code on builds only — at the lowest tier a `has…` trait is set false with a matching rationale unless the description states it (provenance `stated`). A Re-simulate is untouched (it already refuses to switch protections on unasked). One live build of that same e-commerce prompt ($0.0347) showed the prompt works for most traits (rate limiting and two breakers came back off, rationale "typical for a first launch to omit it") but two protections stayed on as `inferred` ("should guard against slow/failing calls" — a recommendation, not a fact), which the `default`-only backstop could not catch. So `startMinimal` now keeps a protection on only when its provenance is `stated`, and the prompt says so; that last change is unit-tested but not re-run live. The stored-build statistics could not be pulled (Supabase MCP unauthorized) so the pre-fix rate is unknown.
