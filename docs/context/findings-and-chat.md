# Findings and chat

> Part of the project context; the index is [`CONTEXT.md`](../../CONTEXT.md). How findings are produced and filtered (typed fields, area decisions, graph facts, ranking), how chat classifies messages, and the decision to stay on Sonnet 5. Read before changing `identifyFailures.ts`, `chatWithProject.ts` or the model choice.

Each section below is one decision: the heading is the decision, the text is the reason and the evidence. A decision marked ~~struck through~~ or "superseded" is kept on purpose, so the reasoning is not lost.

## ~~Chat is for correction, not Q&A~~ — superseded

`chatWithProject.ts` now does both deliberately: the AI itself decides whether a message is a question (answered directly, model untouched) or a change request. A change request is **queued**, not applied: chat returns a restatement plus a self-contained `instruction`, the store keeps it in `pendingChanges` beside the queued fixes, and Re-simulate (`reworkModel`) implements every queued item together — so the canvas only moves on the one deliberate, billed step. Each queued change keeps the user's exact words and the resolved instruction, and chat is shown the whole queue on every message, so nothing is lost as the conversation scrolls out of the history window. Findings still never come from chat — a question's answer is prose, not a new finding — but "never Q&A" is no longer true.

## Two review-noise filters, from one large end-to-end live run

A single Netflix-like system (build → findings → 4 chat messages → Re-simulate with two queued changes and a chosen fix → findings → 10K-user scale step) cost $0.24 with no retries. Two things kept the findings from teaching well: the chosen fix "integrate a secondary payment processor" added `payment-processor-secondary`, which the next review flagged for having no fallback (a standby IS the fallback), so fixes never converged; and "…_AT_SCALE" findings appeared on a 100-user system (2 of 3 real projects). (Superseded — see "Judgment lives in the AI" in [`product-decisions.md`](product-decisions.md): the standby filter was removed, and the at-scale filter now reads a typed field the AI fills.) Checked live afterwards ($0.23, raw AI findings compared with what is kept): on four reviews of three systems at the bottom rung the filter dropped 5 findings, all warnings, 4 of them `UNCACHED_DATABASE_AT_SCALE` and 1 `FIXED_SCALING_AT_SCALE`, and the same `UNCACHED_DATABASE_AT_SCALE` came back, kept, when the same system was reviewed at 10K users (0 dropped there). The standby filter did NOT fire in that run (the situation didn't recur: with the secondary provider added, the model raised no fallback finding at all), so it is unit-tested only. Also seen and left alone: `SINGLE_POINT_OF_FAILURE@gateway` still gets through at 100 users (a gateway has no instance-count trait). Not changed: the 10K-user Re-simulate made no trait changes — unclear whether instance counts were already `multiple` or the auto-set rule didn't fire; a code threshold was considered and REJECTED by the product owner: instance counts are set by the AI from the tier group, not by a number in code. So `tierGuide.ts` gives both the base rework prompt and the extended revise prompt the same four tier groups as guidance for the AI's own per-component judgement (a scheduled job may stay single at any tier), and the rework is told to do it on every Re-simulate, in both directions. Checked live ($0.10, 0 retries; e-commerce system stepped 100 → 10K → 1M → 100 users): at 10K the three services went multiple and only the orders database (state that can't be lost) got replicas while the product database stayed single; at 1M the product database got replicas too; back at 100 everything returned to single — the AI reasoned per component and in both directions. One flaw found and fixed: the provenance carry-forward kept the OLD rationale for an unchanged count ("10,000 users…" on a 1M-user system), so instance counts now keep the previous provenance but take the fresh rationale.

## Stay on Sonnet 5; get depth from scaffolding (findings step)

Opus 5 trial ($0.56, Apex Arena, one sample per arm): 10 findings vs Sonnet's 4, deeper (parallel event paths, a hot leaderboard key, a request-path single point of failure, event schema validation) and plainer titles, but 2.8x the cost ($0.35 vs $0.12 for build + findings), the topology draft about the same, and neither flagged shared-database coupling, regional latency or consistency. Product decision: stay on Sonnet 5 and improve with scaffolding. Implemented for `identifyFailures` (unit-tested only): (1) the AI must decide 8 review areas one by one before listing findings (`considered`: applies + evidence — data-integrity, hot-keys-and-partitioning, regional-latency, shared-datastore-coupling, duplicate-or-parallel-paths, request-path-single-points, cascading-failure, durability-and-recovery), and a decision that disagrees with the findings is rejected and repaired (same device as the per-kind decisions of the propose step); (2) `graphFacts.ts` hands it structural FACTS (stores several components share, how each queue/broker is wired, wide fan-out, parts reached two ways, who calls external systems) to judge — no threshold decides what is a problem; (3) each finding carries an `area` and an `impact` (high/medium/low), and findings are returned ranked by impact then severity. The one live run intended to verify it was cut off by the budget guard before the findings call returned, so the new schema has NOT been accepted by the API yet and the depth gain is unmeasured.
