# Web app decisions

> Part of the project context; the index is [`CONTEXT.md`](../../CONTEXT.md). Decisions about the Next.js app: how leaving a project behaves, the `/project/<id>` URL and login deep links, and AI usage tracking with the operator dashboard. Read before touching routing, auth redirects, autosave or usage tracking.

Each section below is one decision: the heading is the decision, the text is the reason and the evidence. A decision marked ~~struck through~~ or "superseded" is kept on purpose, so the reasoning is not lost.

## Leaving a project never asks "are you sure?" — it saves first

The old "Start a new project? … save it first" dialog told people to save when there's no Save button (autosave does it), and appeared on the blank home screen where there is nothing to lose. `saveBeforeLeaving` (project slice) now runs before starting a new project or opening another: no-op on a blank canvas, no-op when nothing changed since the last save/load (tracked by `savedRevision`, so browsing doesn't bump a project's "updated" time), otherwise it saves — including a moved tier, which autosave deliberately never triggers but leaving would lose — and only a FAILED needed save (offline, signed out) shows a dialog, worded as a discard-or-stay choice. The "New project" button isn't rendered on the blank home screen at all: describing a system in the box there already creates the project. The projects list shows exactly 3.5 rows (fixed row height, cap derived from it in `lib/projectListLayout.ts`) so the half row cues that it scrolls.

## An open project has its own URL: `/project/<id>`

The workspace UI is rendered by the `(app)` route group's **layout** (`components/Workspace.tsx`), with `/` and `/project/[id]` as empty pages, so it's one instance across both — a page-per-route would remount it on every URL change (e.g. autosave giving a new project its first id) and close the chat popup mid-conversation. The URL and the store's `currentProjectId` follow each other by one rule (`lib/projectRoute.ts`, pure and tested, including a simulation that they settle rather than ping-pong): whichever changed since the last decision leads; a deep link wins at load; a first save `replace`s the URL, switching projects `push`es (Back returns to the previous project). A link that can't load (deleted, someone else's, malformed) shows "Project not found" and leaves the open project alone. A deep link followed while signed out survives login: middleware adds `?next=<path>` to the `/login` redirect, the Google flow pushes there, and the magic-link flow carries it in a short-lived cookie (not a query param on the redirect URL — Supabase only honours redirect URLs matching its allow-list, so an extra query string could silently fall back to the site root) that `/auth/callback` reads. `next` comes from a URL/cookie and is redirected to, so every reader goes through `lib/nextPath.ts`'s `safeNextPath` (same-origin path only: rejects `//host`, backslashes, control chars, the login/auth/api paths, and anything that resolves off-origin) and the redirect is always built as `origin + path`. `openProject`/`hydrateFromStorage` resolve `opened | not-found | superseded` so an open that merely lost a race to another click never shows "Project not found".

## Every AI call is tracked (opt-in via `SUPABASE_SERVICE_ROLE_KEY`)

`runStructuredCall` emits an `AiCallRecord` per API request (retries included) through an `onCall` option; the web app's routes record it server-side into `ai_calls` (metrics + cost, kept) and `ai_call_payloads` (full prompt/response, purged after 30 days), keyed by a client-minted `actionId` that each version also stores, plus a client-reported `ai_action_outcomes` for responses paid for but never shown. Tokens are the source of truth; cost is derived and stamped with a price version, and is `null` for a model with no configured price rather than a guess. Writes are server-only (service role, no RLS write policies); tracking failing never fails an AI call. An operator-only dashboard at `/admin/usage` (allow-listed by `ADMIN_EMAILS`, fail-closed, 404 for everyone else) reads it all through one SQL function. See `apps/web/README.md` and `apps/web/db/ai-usage.sql`.

## Guest trial: a real anonymous user with a server-counted quota (off until `TRIAL_ENABLED=true`)

A visitor can "Try it as a guest" without signing up. A guest is a Supabase **anonymous user** (`auth.users.is_anonymous`), not a special mode: projects, `ai_calls` and RLS already key off a user id, so nothing else changes, and adding an email later (`updateUser`, `components/GuestBanner.tsx`) upgrades the SAME account, keeping the diagram and versions. The middleware needs no rule for guests (they have a session); only `/api/trial/status` is public.

- **Quota, counted on the server before the engine runs** (`lib/trial/server.ts` `reserveTrial`, the SQL `trial_reserve` in `db/guest-trial.sql`): 1 build, 1 Re-simulate, 5 chat messages; findings (3) and fix explanations (3) are allowed only after a counted build/Re-simulate, so they can't be called alone. The count is one atomic SQL function (advisory lock per user), so parallel requests can't overshoot. A retry with the same `actionId` is not double-counted. An attempt that fails, is refused by the final gate, or is reported `withheld` is **released** and stops counting. The client is never trusted with the count.
- **Fails closed for a guest**: an error deciding the quota, the trial being off or the service key missing refuses the action (429 `trial-limit`); it fails open only when the caller can't be identified at all (middleware has already required a session). Signed-in users are untouched.
- **Daily budget** (`TRIAL_DAILY_BUDGET_USD`, default $2, UTC day): the sum of `ai_calls` cost for guest accounts. When spent, no NEW guest can start and `/api/trial/status` says `available:false`, so the login page **doesn't show the guest option at all** (not disabled). A guest already mid-trial finishes their quota.
- **Abuse limits**: at most `TRIAL_MAX_ACCOUNTS_PER_IP` (default 3) guest accounts per hashed IP per day, enforced when the account first uses the AI (so calling Supabase's anonymous sign-in directly doesn't bypass it). Only a salted SHA-256 of the IP is stored (`TRIAL_IP_SALT`). `purge_anonymous_users(days)` deletes old guest accounts. The admin dashboard labels them "Guest xxxxxxxx".
- **Bot check** is an off-by-default switch: `NEXT_PUBLIC_TRIAL_CAPTCHA=true` + `NEXT_PUBLIC_HCAPTCHA_SITE_KEY` shows an hCaptcha widget and sends its token with `signInAnonymously`; the secret goes in Supabase (Auth → Attack Protection). Not enabled or tested against a real hCaptcha yet.
- **Signed-in users get the same quota (until credits exist).** `reserveTrial` limits everyone except admins (`ADMIN_EMAILS`) to 1 build / 1 Re-simulate / 5 chat, lifetime per account, so a signed-in user can save one project ("New project" is shown disabled, `useTrialStatus` + `/api/trial/me`). Only guests are held to the daily budget and per-IP cap (`trial_accounts.is_guest`); the refusal wording differs ("credits are coming" vs "sign in"). `TRIAL_ENABLED=false` leaves signed-in users unlimited. This is a placeholder for the credit system, to be designed after guest mode is verified. A guest who upgrades keeps the same account and the same used quota.
- **End of trial**: a refused action keeps the diagram on screen; the banner turns into "add your email to keep it".

Setup the operator does: enable "Allow anonymous sign-ins" in Supabase Auth, run `apps/web/db/guest-trial.sql`, set `TRIAL_ENABLED=true` (and optionally schedule the purge). Unit-tested only (mocked Supabase); never run against a real database or in a browser.

## Branding, SEO and the public surface

Name is **CuriousArch** ("Curious" light, "Arch" bold) in Space Grotesk, used ONLY for the wordmark (`components/Wordmark.tsx`); content stays in Geist so the name reads as a logo. The mark is drawn inline (`components/Logo.tsx`, follows `currentColor`); `app/icon.svg` is the tab icon; the PNGs (iOS icon, social cards, PWA icons) are generated by `apps/web/scripts/generate-brand-assets.mjs`. Constants (name, tagline, description, origin) live in `lib/site.ts`; `NEXT_PUBLIC_SITE_URL` must be set before a production build. The app is behind login, so the root layout is `noindex` and `/login` is the only indexable page (own metadata + JSON-LD in `app/login/layout.tsx`); `robots.ts` disallows `/api`, `/admin`, `/project`, `/auth`; `sitemap.ts` lists `/login`. `middleware.ts` was renamed `proxy.ts` (Next 16 deprecation, same behaviour) and its matcher now excludes `robots.txt`, `sitemap.xml`, `manifest.webmanifest` and `/api/health` so crawlers and uptime probes are never redirected to login (tested in `tests/site-seo.test.ts`). Baseline security headers are set in `next.config.ts`; a CSP is not (needs a browser-tested nonce policy). Deployment steps and the remaining pre-launch gaps are in `docs/DEPLOYMENT.md`; every env var is in `apps/web/.env.example`.

`/privacy` and `/terms` are public (proxy allows them signed out, robots/sitemap list them, linked from the login footer). They are drafts written from what the code does (`components/LegalPage.tsx`, `lib/site.ts` `LEGAL_UPDATED`/`contactEmail`) and need a lawyer's review before paid launch; bump `LEGAL_UPDATED` whenever data handling changes (e.g. when billing is added).
