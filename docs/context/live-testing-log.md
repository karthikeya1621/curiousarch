## The minimum reliable flow is build + chat-requested change, checked by a scripted live eval

Goal stated by the product owner: a reliable baseline that others then refine through the AI chat, so build and "chat request → Re-simulate applies it" matter most. A throwaway script (six systems: build, one chat change each — add CDN, insert queue, rate-limit, remove cache, add service, split service — then Re-simulate) checks invariants: unique ids, no dangling/duplicate edges, clean name, no lint findings, no unrequested protection flipped, no unasked id loss, requested effect present. Findings from two runs: 0 failed attempts on nearly all calls and the requested effect present every time it was well-posed, but (1) two of three video builds wired a direct edge AND a broker path (base and extended calls disagree) → `collapseParallelAsyncPaths` now keeps the buffered path and drops duplicate edges on every build and Re-simulate; (2) chat queued no-op changes ("remove the cache" when none exists; "add a queue" when one does) → the route prompt checks for already-true/impossible first, and a reply that ends in a question is never queued (code). Remaining variance: an ambiguous request gets an inconsistent restatement (once it invented an edge to delete). The script is now checked in as `packages/engine/scripts/eval-live.ts` (`npm run eval:live`, costs money, exits non-zero on a broken invariant). A later pass on eight scenarios was 8/8 clean with 2–3 retries, each traced and fixed in code: workload targets are snapped to the ladder (`snapToLadder`); an edge to an id the user's own request names but the base call can't emit is dropped (`dropEdgesToMentionedUnknowns`); a request the extended step owns skips the base-only edge check and lost connections are restored on the merged graph (`restoreDroppedConnections`); extended components get the same provenance/protection reconciliation as base ones. Re-verified live afterwards: two runs of the eight small scenarios had 0 retries (one scenario each run missed once: an unqueued-consumer queue, and an object-storage request that never produced storage). Five LARGE systems (Netflix, Uber, Amazon, Twitter, Slack-like; `EVAL_SET=large`) were 5/5 clean with 0 retries, 12–16 components (the 15-component cap is hit, by design), $0.06–0.08 each for build + chat + Re-simulate (findings not included). The eval prints cost per scenario. The chat restatement was inventing kinds (`storage`, `message-queue`), so the route prompt now lists the valid ones.

## Six follow-ups from the all-features project (then run live for $1.19 — see the last sentence)

(1) `EVAL_SET=flows` in `scripts/eval-live.ts`: a scale-step flow (10K → 1M with nothing queued: no extended or base component may vanish, no rationale may still say "starting tier") and a chat conversation (already-true, "No.", absent, "No. Ignore it" must queue nothing; only the real change queues) — the two gaps the earlier eval never covered. (2) `checkNoDroppedBaseComponents`: with nothing queued a rework may not silently drop a base component (mirror of the extended guard). (3) Both reworks are told to add a component only when a fix/request asks or the system can't work without it, never because such systems typically have one. (4) Tier-driven values follow the tier: `tierGuide.ts` now also says which protections are BASELINE at the third tier and above (rate limiting on a public gateway, health checks on a load balancer, a timeout on an external call; everything else stays off), for components kept AND added, in both directions; `reconcileWithPrevious` only holds unasked protections off at the LOWEST tier; a `stated` value survives when a request is queued (the user stated it); at the lowest tier with nothing queued `startMinimal` returns inferred protections to off after a scale-down. Trade-off: fewer of those findings at high tiers. (5) `reviewGraph.ts`: one small Haiku call looks at the merged graph plus the user's request and returns edge edits (remove/reverse/add) that code only validates (ids exist, acyclic, nothing orphaned, a removed edge stays connected by another path, ≤ 8); skipped when there is no queue/broker/balancer/CDN; on success it replaces the hard-coded collapse/route rewrites, which remain the fallback if it is skipped or fails; it never fails a build. (6) The revise step returns `keep` (ids left exactly as they are), `components` (only added/changed, in full) and `remove` (only when asked) instead of re-emitting everything each Re-simulate; a previous component named nowhere is a dropped one and is rejected; the prompt says to keep only a component whose rationales are still true at the current scale, which is how it stays compatible with fresh rationales. Live results ($1.19 over 8 runs; flows 2/2 clean, small 7/8 clean, 0 retries in the final runs): the strict schemas for revise (keep/remove), propose (considered), the graph review and the chat `intent` were all accepted; the scale flow kept all five extended components at 10K and 1M and set instance counts from the tier group (services multiple at 10K; database replicas and the balancer multiple at 1M); the chat conversation queued only the real change. Defects the live runs exposed and that were then fixed: (a) the propose step answered with an EMPTY list about 1 build in 4 for a description naming five extended parts (a 57-token reply) — it now must decide each of the seven kinds (`considered`: needed + evidence) before listing components, and a decision that disagrees with the components is rejected and repaired; 6/6 builds afterwards returned all five; (b) the graph review on the small model misread edge direction (proposed removing a balancer's edge to the gateway and reversing a CDN's correct edge) — it now uses the main model, never handles CDN edges (their direction is settled deterministically at merge), and code rejects any edit that points an edge into a CDN or removes an edge that nothing else connects; (c) with ANY request queued, the lowest-tier guard stood down and an unrelated request switched on gateway rate limiting — at the lowest tier an unasked protection is now reverted unless it is labelled `stated` (the convention: a value a request asked for is `stated`), and `startMinimal` runs whether or not something is queued; (d) the eval's own invariants were out of date (a requested value is `stated`; no queue needed when the build already has it). Verified live afterwards in one more flow ($0.13; build → 1M → back to 100 → chosen fix): the review looked at a build with a load balancer and a queue and correctly changed nothing; at 1M services and the balancer went multiple, the database got replicas, the gateway's rate limiting and the balancer's health checks came on as `inferred` (the baseline for that tier) while the notification service stayed single; back at 100 everything returned to single and every inferred protection went off, the description's stated payment timeout stayed; a chosen fix (dead-letter queue) came back `stated` with nothing else changed; and the extended-component guard fired live — on the scale-down the revise step dropped the load balancer, was rejected with the reason, and repaired it. Still unverified live: the base dropped-component check and review edits that actually change something.

## Live round on the all-features description ($1.31): six more defects found, fixed and re-checked

Run in the order a user would (build → findings → "add a second load balancer" → "keep the gateway direct" → 10K → 1M): (1) a STATED gateway rate limit was switched off at 10K users (the AI read "second tier: no protections" as covering it) → `reconcileWithPrevious` now reverts any change to a `stated` trait unless something was queued; (2) the second balancer was silently not added because the description had already used all 6 extended components, and the chat said it was queued → the chat prompt now states both totals and the room left ("15 base, 6 extended, no per-kind limit") and an add past a full group is `no-change`; stating the limit made the model invent a per-kind limit of two, so the prompt now says nothing else is a limit — verified: at the cap it answered correctly, with room it queued; (3) with room, the base call improvised a base-kind stand-in ("lb-meeting", a service) for the requested load balancer → the chat route now returns `affectsKinds` (a typed field), the queued change carries `kinds`, and a change that is only about extended kinds (or a fix on an extended component) is NOT shown to the base call — only to the revise step; two live runs afterwards both produced a real `load-balancer` routed in front of the service; (4) the graph review returned no edits for a newly added balancer whose caller still bypassed it (and, on other runs, invalid edits) — the deterministic rewrites now ALWAYS run after it, and it only runs when a new queue/broker/balancer was added; the review has still never made a useful edit in ~10 calls, so it is a candidate for removal; (5) the propose consistency check caught the model's inconsistencies live in the final eval ("needed but not returned", a missing kind) and repaired them; (6) eval invariants updated. Final full eval (small + large + flows, $0.72): 14/15 clean, 2 retries, both from the propose consistency check, $0.02 wasted.

## Full live coverage run on a new large system ("Apex Arena", a 1B-player multiplayer platform; $0.53)

One script walked every engine feature in the order a user would: build (title, tier/target snapping, the six extended decisions, stated vs minimal protections, CDN direction, balancer placement, lint), findings (typed fields, hold-back, filters), explainFix, a 9-message chat (question; already-true, absent and "No." queued nothing; base-only, extended-only and mixed changes queued with the right `kinds`; a second CDN at the extended cap answered), a Re-simulate applying three queued changes (an asked-for removal allowed, nothing else lost), a chosen fix, scale up through 10K/1M/100M, findings at 100M, and scale back down. 65/67 checks passed with 0 retries. The two "failures": a wrong check (at the top rung nothing can bite "at a larger scale", so 0 held-back findings is right) and one real defect — scaling straight from 100M to 100 left every service `multiple` and the database `has-replicas` (protections went back off because code returns them; instance counts are the AI's call and it did not). Fix: `checkLowestTierMinimal`, a CHECK not a rewrite — at the lowest tier with nothing queued, an instance count above `single` or a consumer scaling above `fixed` that is not `stated` is rejected with the traits named and the AI repairs it (base call and revise step alike); verified live ($0.13): the check fired on the first attempt and the repair returned every count to single. Also found: the AI drew the pub/sub broker with a publisher and NO subscribers in 2 of 2 builds although the description named three subscribers → lint rules `BROKER_NO_SUBSCRIBER` / `BROKER_NO_PUBLISHER` (the queue rules' twins) so the gap shows as a finding with a fix. Not testable from here (no browser/Supabase): the project list, routes and auth, autosave and versions restore, the Controls buttons, the diagram, the chat panel and `/comp` picker, usage tracking and the admin dashboard.
