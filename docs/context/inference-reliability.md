# Inference reliability: checks, continuity and the final gate

> Part of the project context; the index is [`CONTEXT.md`](../../CONTEXT.md). Everything that stops a wrong result reaching the user: validation classes, continuity checks (edges, components, extended components), identity cleaning, the description-coverage check, the final gate and safe fallback, and friendly errors. Read before touching `structuredCall.ts`, `reworkModel.ts`, `fromProse.ts`, `extendedComponents.ts` or `finalGate.ts`.

Each section below is one decision: the heading is the decision, the text is the reason and the evidence. A decision marked ~~struck through~~ or "superseded" is kept on purpose, so the reasoning is not lost.

## `reworkModel`'s prompt warns against every validation-failure class strict mode can't prevent

Strict mode's constrained decoding guarantees the JSON *shape* is valid; the only failures a repair-retry can still hit are Zod's own semantic checks (duplicate id, edge to a nonexistent id, a cycle, a placeholder rationale) — each one costs a full extra billed call (the whole invalid output gets re-sent as input). `schema.ts`'s `STRUCTURAL_SELF_CHECK` names all four and is interpolated into `REWORK_PROMPT`, which — unlike `fromProse`'s prompt — hadn't warned against the first two; rework edits an existing graph, which is exactly where a removed component's edge is left dangling or an id gets reused by accident. Verified live via the read-only Supabase MCP connection: a real Re-simulate cost 3 rework attempts (2 of them retries) hitting exactly these two classes — a literal `"placeholder"` rationale and edges to ids not in the AI's own output. The first prompt fix alone didn't help; the retry rate held, and a second retry reproduced the identical `"placeholder"` text on the identical field. Root cause: `fromProse`/`extendedComponents`/the new checklist all spelled out the exact banned word ("placeholder") as the negative example, and the validator's own repair-retry message doubled it (`"placeholder" is a placeholder, not a reason`) — a known LLM priming failure mode, not a schema gap. Fixed by rewriting every prompt AND the validator's own error messages to describe the category without repeating the literal banned token (still confirms the model's bad value verbatim for debuggability, just not paired with the same word as the category label). Not yet re-verified after this second fix — check `ai_label_stats.retry_pct` for `reworkModel`/`reviseExtendedComponents` after the next few Re-simulates.

## The base rework call is never shown the extended components

Found live across four Re-simulates (Instagram twice, YouTube once, and the earlier one): shown the extended components (CDN, object storage, load balancer, scheduled job…) and told to leave them out while also preserving every edge, the model kept re-emitting them — as fake base-kind stand-ins filled with placeholder text (where the recurring `"placeholder"` rationale actually came from; my earlier "the prompt primes it" theory was incomplete), or as edges to ids missing from its output — and every mistake was a full billed retry re-sending the whole model (about two thirds of a rework's cost in the YouTube run). `reworkModel.ts`'s `baseView` now removes them and their edges from the base call's input (a note names them by kind and label, never id), and `stripExtendedReferences` (via a new `normalizeOutput` hook on `runStructuredCall`, applied before Zod) drops any reference that still arrives through the user's own queued text. The same run showed the revise step had never been shown the existing edges, so it re-invented the wiring — a background job and a CDN ended up with no incoming edge, which the canvas draws as user traffic flowing straight into them. It now receives the original edges touching the extended components, and `checkNoDroppedExtendedEdges` (a `validateResult`, same mechanism as the base check) rejects a result that drops or reverses one. Known limit: both continuity checks treat any dropped edge between two kept components as an error, so a request to remove a connection WITHOUT removing a component would fail its retries; removing a component is exempt, which covers the normal cases.

## Rework keeps the connection, not the literal edge; and says only what it changed

Found on the Zoom project (see the usage dashboard): the input had one edge listed twice, the user chose "insert a queue between A and B", the AI did exactly that, and `checkNoDroppedEdges` rejected it (a $0.02 retry) — then the retry kept the direct edge too, leaving two competing paths. The check now compares unique pairs and accepts a path through an inserted component; edges are deduplicated on input and output. The same project showed the first scale-up switching on rate limiting, breakers and stampede protection unasked (leaving the review nothing to find) and provenance drifting to "stated" for values nobody stated. `reconcileWithPrevious` (a `normalizeOutput` step) now restores unchanged traits' provenance/rationale, caps changed ones at "inferred", and reverts a `has…` protection flipped on when no fix or chat change was queued. `identifyFailures` drops findings whose code names another kind's trait (`LB_*` on a gateway). The dashboard says what a clean review means and to raise the scale next.

## A project's id and name are never the AI's to change

A Search-engine project's title became the literal text `{"value":"Google Search Engine (Core Request Path)"}`: a Re-simulate returned the name wrapped like a trait (once the `id` held a dump of the whole model), it is a valid string so nothing rejected it, and every later rework copied it forward. `reworkModel` now takes `id`/`name` from its (cleaned) input and overwrites whatever the AI returned; `fromProse` cleans its own; `unwrapIdentityText`/`cleanModelIdentity` (types.ts) unwrap the known shapes; and `loadProject`/`listProjects` heal already-saved projects as they are read (the next save writes the clean name back, no migration). The extended step's dropped-edge check got the same connection-not-literal-edge relaxation as the base one: on that project it rejected the queue-inserting fix (a retry) and the retry kept both paths. `identifyFailures` is also told to judge risks at the CURRENT scale (a 100-user system was getting critical "at scale" findings).

## Found in the app on the all-features project (5 versions, $0.27, 0 retries): three defects

(1) A Re-simulate at 1M users with nothing queued handed the revise step six existing extended components and it returned an empty list — payment provider, push provider, CDN, recording storage, nightly job and API load balancer vanished, no check caught it (a missing component exempts its edges), and the next Re-simulate re-invented different ones (a media balancer and a TURN relay nobody described). `checkNoDroppedExtendedComponents` now rejects it when nothing is queued (AI repairs on retry); with a request queued removal may be intended, so no check. (2) Chat queued acknowledgements ("No.", "No. Ignore it" → "Understood." as a queued change): the route had no place for a message that changes nothing, so the two booleans became one `intent` (`change` / `question` / `no-change`); only `change` queues. (3) Rationales went stale after a scale change ("off at this starting tier", "still single at 10k tier" on a 1M-user system) because unchanged traits carried their old rationale forward; now only the provenance is carried, the rationale is fresh, and both prompts say a rationale must be true at the current scale. All unit-tested only. Observed, not changed: new components added at a higher tier arrive with protections on as `inferred` (health checks, a timeout), which sits uneasily with "protections only if stated".

## Three reliability improvements: a description-coverage check, the graph review removed, and Re-simulate changes made visible

(1) `coverage.ts`: after the base draft, a small call lists every part the description names and which drafted component covers it (owner `base` / `extended` / `not-built`, componentId `""` when nothing does); a base part nothing covers triggers exactly ONE more draft (`fromProse:complete`) with those parts spelled out; skipped near the component cap; never fails a build. It was first written with a `none` owner and the AI used it to say "nothing models this" for the three subscribers (0/3 triggered) — renamed `not-built` and defined as "never built or run", after which 3/3 Apex Arena builds triggered the second draft and the subscribers (analytics, anti-cheat, notifications) appeared wired to the broker, while 2/2 URL-shortener builds triggered nothing; cost +$0.006 per build, +$0.01 when it triggers. (2) `reviewGraph` was REMOVED: in ~10 live calls it made no useful edit (empty lists, invalid edits, one wrong CDN reversal) and the deterministic rewrites always did the work; the rewrites stay for now, with a build-level integration test. (3) Web: `lib/modelDiff.ts` (added/removed components, changed trait values, changed connections); the version list shows what each Re-simulate changed ("+1 component, 3 values changed…"); and `commitRework` sets `reworkWarning` when components were removed although nothing was queued that could have asked for it — a banner names them and points at Version History. Unit-tested only: no browser was available.

## Paid-product safety: a final gate on every result, a safe fallback, and no raw errors to customers

Product owner: people will pay, so silly mistakes must not reach them. `finalGate.ts` (`checkFinalModel`) runs every HARD rule — the ones needing no design opinion — on the finished model against the one it replaces: clean id/title, unchanged id/title and workload, unique ids, no dangling/duplicate/self connections, no cycle, nothing floating, base ≤ 15 and extended ≤ 6, no edge into a CDN, at the lowest tier no protection on unless stated and (with nothing asked) nothing scaled past the minimum, and — with nothing queued — no removed component, no lost connection (a turned-around CDN edge is a correction, not a loss) and no stated value changed. `fromProse` and `reworkModel` call it: on a violation the whole step is retried ONCE with the violations spelled out, and a second failure throws `ModelGateError` — nothing wrong is returned. The API routes answer a `ModelGateError` with 422 `{ code: "unsafe-result", error: "We couldn't apply this safely, so nothing was changed…" }` (the client reports the attempt as `withheld` so it can be excluded from billing) and every other engine failure with a friendly 502 that no longer carries truncated model JSON or provider billing text (the real error is logged; `detail` only outside production). Deliberately not in the gate: judgments (is a CDN origin sensible, is a shared database a risk). Unit-tested only, including a merge-level violation no single step catches (an extended component wired to nothing); not yet run live. Still open for a paid launch: billing that honours `withheld`, a larger live eval against the gate, a browser click-through, and a professional review.

## A schema-valid rework result can still be substantively wrong — code now catches it

Confirmed live via the Instagram-project comparison: a first attempt catastrophically malformed its tool call, and the repair-retry "fixed" it by patching only the two reported Zod errors onto that broken skeleton — schema-valid, but missing 8 of 9 edges and the entire requested feature, and nothing caught it before it shipped as the new version. `runStructuredCall` (`structuredCall.ts`) now takes an optional `validateResult` hook, run after Zod validation succeeds, for an invariant Zod structurally cannot check (it never sees the ORIGINAL input, only the proposed output). `reworkModel.ts`'s `checkNoDroppedEdges` enforces, in code, the continuity rule its own prompt already stated but didn't enforce: an edge between two components the result kept must still be present, unless the request asked for its removal. A violation is billed and repaired exactly like a Zod failure (same retry loop, same usage-tracking `outcome: "invalid"`), not a separate path. Scoped to `reworkModel` only for now — `reviseExtendedComponents` isn't covered, since the evidence pointed at the base call specifically.
